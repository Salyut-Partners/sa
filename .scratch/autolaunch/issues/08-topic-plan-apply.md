# 08 — Топік на платформі через plan/apply

**What to build:** байер пише `topic.yaml`, викликає `sa plan` і бачить повний список того, що станеться, з тілами запитів; `sa apply --confirm` створює топік і конфігурацію на платформі, записує id у `state.json`, і повторний виклик нічого не робить. Це перша наскрізна нитка заливу: клієнт digifor з токеном і org id з конфігурації; політика черги в `core` як чиста функція (без пауз на читання, джитер між записами кроку, паузи між кроками й кампаніями, read-back перед ретраєм); `apply` як задача сервера з прогресом, скасуванням і відновленням зі `state.json`; знімок «до» пишеться до відправки. Гейт: `sa apply` без явного підтвердження відмовляється, а в налаштуваннях Claude Code монорепо стоїть deny на цю команду.

**Blocked by:** 03 — `sa new`.

**Status:** ready-for-agent

- [ ] `sa plan` на теці без `state.json` показує два кроки з тілами й нічого не створює, скільки б разів не запускався
- [ ] `sa apply --confirm` створює топік і конфігурацію; `state.json` містить обидва id; другий `apply` показує порожній план
- [ ] Обрив після створення топіка, але до запису стану, при повторі знаходить топік read-back і не створює другий
- [ ] Політика черги покрита тестами: таймаут дає read-back, повтор іде після нього, паузи різні для читань, записів і кроків
- [ ] `sa apply` без підтвердження виходить з ненульовим кодом; deny для Claude записаний у налаштуваннях монорепо
