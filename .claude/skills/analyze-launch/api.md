# Reporting API (Digifor / Roots) — конфіг для analyze-launch

**Статус: налаштовано, перевірено живими викликами 2026-08-11; поля кліків
перевірені повторно 2026-08-18 (див. «Три кліки» нижче).**

- **Система:** Roots platform (адмінка — https://admin.digifor.io/analytics)
- **База API:** `https://admin-api.digifor.io/api/reporting/v1`
- **Автентифікація:** `Authorization: Bearer <токен>` + `Accept: application/json`.
  Токен лежить у файлі **`secret/api-key-roots`** (тека в `.gitignore`, у
  репозиторій не потрапляє). У команду підставляй так, щоб не друкувати:
  `TOKEN=$(tr -d '[:space:]' < secret/api-key-roots)`.
- **Скоуп токена: вся організація** (Salyut Partners) — API віддає кампанії
  всіх байерів. Розріз «байер бачить своє» робиться на нашому боці по
  маркеру байера в неймінгу (див. нижче). Байеру чужі цифри не показуй —
  фільтруй перед видачею. (Майбутній скіл для керівника — ті самі виклики
  без фільтра по маркеру.)

## Ендпоінти

Обидва — `GET`, обидва приймають лише два робочі параметри:
`date_type` = `today` | `yesterday` | `last7days` | `MM/dd/yyyy-MM/dd/yyyy`
(слеші в URL кодуй як `%2F`) і `topic_id` (серверний фільтр, працює на обох;
недокументований, але перевірений). Решта параметрів (`campaign_id`,
`status`, `country`, `traffic_source`…) **ігноруються мовчки** — фільтруй
через `jq`.

### 1. `/campaigns` — зріз по кампаніях (спенд, ROI, сетап)

Один рядок = одна кампанія, **агрегат за весь запитаний період, поля дати в
рядках нема**. Динаміка по днях = цикл по днях, один виклик на день
(`date_type=08%2F09%2F2026-08%2F09%2F2026`).

Поля рядка: `campaign_id`, `campaign_name`, `status` (ACTIVE/PAUSED),
`traffic_source`, `topic_id/topic_name/topic_internal_name`, `country`,
`bid`, `bid_strategy`, `budget`, `language`, `theme` (макет лендінга),
`term_group` (група ключів), `revenue`, `spend`, `profit`, `roi`,
`clicks`, `s_clicks`, `cpc`, `rpc`, `rps`, `t_cpa`, `s_cpa`,
`g_pctr`, `g_ctr`. Плюс `summary` за період: revenue/spend/profit/clicks
по організації.

⚠️ **Гроші (`revenue`, `spend`, `profit`, `roi`) бери прямо — вони сходяться
з дашбордом. Усе, що ділиться на кліки (`s_clicks`, `cpc`, `rps`, `rpc`), —
не бери прямо**, воно рахується не на тому знаменнику. Розбір нижче.

### 2. `/revenue` — ревеню по годинах (виплата, дроп дня)

Один рядок = кампанія × година: `date`, `hour`, `topic_*`, `campaign_*`,
`revenue`, `clicks`, `rpc`. **Спенду тут нема.** Діапазон дат віддає всі дні
з датою в рядку — для «ревеню по днях» достатньо одного виклику.

Коди відповідей: 200; 403 — невалідний токен; 404; 500.

## Три «кліки» — головна пастка API

У системі одночасно живуть **три різні знаменники кліків**, і поле `s_clicks`
з API — **не той sClicks, який байер бачить у дашборді**. Приклад, на якому
спіймали: кампанія `34-FRMVLACOUGC23-TG-1-tk-be-ba-0808-GE09`, 7 днів —
API `s_clicks: 135`, дашборд `sClicks: 29`. Це не округлення, це різні числа.

| Клік | Де живе | Що з ним рахують |
|---|---|---|
| `s_clicks` (сирий) | тільки API | внутрішній, ширший тип кліка; з нього API рахує `cpc` і `rps` |
| **реальний sClicks** | колонка `sClicks` у дашборді | оплачувані кліки — те, що бачить байер; напряму API не віддає |
| `clicks` = gClicks | API і дашборд | пошукові/лендінгові кліки; з них блок «Per Click Data»: `rpc` і `t_cpa` |

**Як дістати реальний sClicks** — через `s_cpa`, яке збігається з колонкою
`s.CPA` дашборда:

```
real_sclicks = round(spend / s_cpa)
real_cpc     = s_cpa                          # ціна оплачуваного кліка
real_rps     = revenue / real_sclicks         # = s_cpa × revenue / spend
```

Перевірено: байер звірив формулу на 11 рядках дашборда — збіг на всіх;
на живому зрізі 2026-08-18 (364 кампанії) тотожності підтвердились точно —
`cpc = spend / s_clicks`, `rpc = revenue / clicks`, `t_cpa = spend / clicks`.

**Множника «поділи на 4» не існує:** відношення `s_clicks / real_sclicks`
на живих даних гуляє від 1 до 8.6 по кампаніях того самого заливу.
Реконструюй щоразу, ніколи не масштабуй коефіцієнтом.

Що з цього випливає для видачі:

- **`s_clicks`, `cpc`, `rps` байеру не називай** — вони не зійдуться з його
  дашбордом, і розмова піде на з'ясування, хто помилився. Треба ціну кліка —
  кажи `s_cpa`.
- **`s_cpa = 0` при `spend > 0`** — реконструкція неможлива, але це й не
  потрібно: на живому зрізі це 150 рядків, з них лише один із ревеню,
  медіанний спенд $0.41 — мікроспендові кампанії без жодного оплаченого
  кліка. Читай як «оплачуваних кліків нема», а не як діру в даних.
- **`clicks` (і залежні `rpc`, `t_cpa`, `g_ctr`) часто нуль при живому
  ревеню** — 185 рядків із 214 ревенюсних на тому ж зрізі. Тобто RPC-лінза
  сліпа на більшості кампаній.
- Гроші — `revenue`, `spend`, `profit`, `roi` — від знаменника кліків не
  залежать, тому головна діагностика (ROI, спенд, «скільки з 10
  відпрацювало») цією пасткою не зачеплена.

Гіпотеза про причину (не підтверджена, лише спостереження): `s_clicks`
рахує ширший тип кліка — схоже, всі кліки по оголошенню до фільтрації, —
а дашборд показує саме оплачувані, і це друге число API наружу віддає
тільки через `s_cpa`.

## Неймінг кампаній — головний ключ розбору

```
34-<topic_internal_name>-<term_group>-<сорс>-<гео>-<маркер байера>-<MMDD запуску>-GE<номер>
приклад: 34-VadimAvtoFR1-tg_avto_ded_FR-tk-fr-bv-0810-GE02
```

`term_group` може містити дефіси — сегменти зв'язки бери **з кінця**:
`[-1]` номер у пачці, `[-2]` дата запуску MMDD, `[-3]` маркер байера,
`[-4]` гео, `[-5]` сорс (`tk` = TikTok).

- **Зв'язка ↔ topic.** `topic_id` — серверний фільтр, ним звужуй обидва
  ендпоінти. topic_id зв'язки знайди по імені/гео в зрізі `/campaigns`.
- **Залив (запуск) = кампанії одного topic з однаковим MMDD.** «Скільки з
  10 відпрацювало» рахується по такій пачці.
- **Байер = маркер `[-3]`** (легасі-маркери у видачі: `bv`, `ba`, `v`; нові —
  4-літерні за стандартом нижче). Маркер байера спитай один раз на початку
  розмови, якщо ще не знаєш.

## Рецепти

```bash
TOKEN=$(tr -d '[:space:]' < secret/api-key-roots)
B="https://admin-api.digifor.io/api/reporting/v1"
AUTH=(-H "Accept: application/json" -H "Authorization: Bearer $TOKEN")

# 1. Знайти зв'язку байера: кампанії за період, тільки його маркер
curl -s "$B/campaigns?date_type=last7days" "${AUTH[@]}" |
  jq '[.data[] | select((.campaign_name | split("-")[-3]) == "bv")]'

# 2. Зріз заливу: topic + день (цикл по днях від дати запуску)
curl -s "$B/campaigns?date_type=08%2F09%2F2026-08%2F09%2F2026&topic_id=92328" "${AUTH[@]}"

# 3. Ревеню по днях/годинах зв'язки (дроп виплати) — один виклик
curl -s "$B/revenue?date_type=08%2F04%2F2026-08%2F10%2F2026&topic_id=92328" "${AUTH[@]}"

# 4. Зріз із реконструйованим sClicks (тим, що байер бачить у дашборді)
curl -s "$B/campaigns?date_type=last7days&topic_id=92328" "${AUTH[@]}" |
  jq '[.data[] | {campaign_name, spend, revenue, roi,
                  sclicks: (if .s_cpa > 0 then (.spend / .s_cpa | round) else 0 end),
                  cpc: .s_cpa}]'
```

## Стандарт неймінгу (діє з 2026-08-11, нові запуски)

Погоджений куратором формат. Старі кампанії **не перейменовуються** — парсинг
з хвоста працює для обох поколінь. Кампанії поза стандартом скіл підсвічує
байеру одним рядком (лінт-регекс нижче), без моралі — порядок наводиться
новими запусками.

**Правило нуль:** усередині сегмента — тільки `a-z`, `0-9`, `_`; дефіс —
виключно роздільник сегментів; усе в нижньому регістрі. Жодних пробілів,
тире, дужок, слешів, кирилиці.

**Кампанія:**

```
34-<topic>-<tg>-tk-<гео|пул>-<байер>-<MMDD>-GE<##>
```

**Topic** (батч креативів):

```
<гео|пул>_<вертикаль>_<кут>_[мова]_<байер><NN>
fr_credit_confiscated_vadk01      кредити, конфісковані авто, Франція, батч 01
be_rent_nodeposit_ar_vadk02       оренда без депозиту, Бельгія, арабська на мігрантів
```

- **вертикаль — повним словом**, закритий словник, 1:1 до фасетів бази:
  `rent`=оренда · `credit`=кредити · `finance`=фінанси · `jobs` ·
  `dental` · `season`=сезонка;
- **кут — одним зрозумілим словом** (`confiscated`, `packing`, `nodeposit`,
  `vineyard`), не абревіатурою;
- **мова** — дволітерний код, тільки коли це не нацмова гео;
- **NN** — порядковий номер батча; ніяких `NEW`/`TEST`/`FINAL`.

**Term_group:** `tg<N>_<напрям ключів>` — `tg1_leasing`, `tg2_b2b_stock`.
Ніколи голе `tg1`/`TG-1`, без дефісів. **Після запуску в платформі не
перейменовувати** — інакше поле й назва кампанії розсинхронюються.

**Маркер байера — 4 літери: перші три імені + перша прізвища** (латиницею).
Реєстр:

| Код | Байер | Легасі-маркер |
|---|---|---|
| — заповнити — | | `bv` |
| — заповнити — | | `ba` |
| — заповнити — | | `v` |

**Гео:** ISO-код країни; пули — тільки зареєстровані тут коди (замість
`intl`). Реєстр пулів: — поки порожній, заповнюється при першому пулі —.

**Лінт-регекс** (нові кампанії):

```
^34-[a-z]{2}(pool)?_(rent|credit|finance|jobs|dental|season)_[a-z]+(_[a-z]{2})?_[a-z]{4}[0-9]{2}-tg[0-9]+_[a-z0-9_]+-tk-[a-z]{2}(pool)?-[a-z]{4}-[0-9]{4}-GE[0-9]{2}$
```

## Що API дає для менторських лінз

| Лінза скіла | Звідки |
|---|---|
| скільки з 10 відпрацювало | `/campaigns` по пачці (topic + MMDD): частка з `profit > 0` |
| спенд іде / мікроспенд | `spend` по кампаніях; стоп на $1–2 видно одразу |
| ROI по днях, не кумулятивно | `/campaigns` циклом по днях |
| просадка дня = дроп виплати | `/revenue`: **`revenue` по днях/годинах**; `rpc` там читай, лише якщо `clicks > 0` (на більшості кампаній нуль) — інакше зіставляй ревеню дня з реконструйованим sClicks зі `/campaigns` за той самий день |
| ціна кліка / скільки кліків купили | `s_cpa` і `round(spend / s_cpa)`, **не** `cpc` і `s_clicks` |
| бід-сітка чи один бід | `bid` по кампаніях пачки: однаковий всюди → один аукціон |
| чи заливався щодня | MMDD у назвах кампаній байера — пропуски дат видно |
| бюджет душить | `budget` проти `spend` |
| куди розносити | `term_group` × `theme` × `country` — що ще не покрито |

## Чого API не знає — питай байера

Бан/стан кабінета, домен (вік, чи платив), креативи всередині кампанії
(вигорання, канібалізація на рівні варіацій), причина паузи. `country` в
кампаніях часто `All` — реальне гео бери з сегмента назви `[-4]`.
